## Communication style

- Wants the assistant to act as a hands-on teacher throughout the build, not just a code generator. Confidence: 1.0
- Explain the "why" and the problem an approach solves in plain language *before* writing code for a new feature or concept. Confidence: 1.0
- After writing code, walk through what it does piece by piece — don't just drop a file and move on. Confidence: 1.0
- Use analogies where helpful for hard concepts (e.g., Operational Transformation, WebSockets, JWT flows). Confidence: 0.95
- Pause and explain any new library, tool, or pattern (JWT, middleware, WebSocket servers, OT transforms, Prisma relations) on first introduction before using it. Confidence: 0.95
- Treat the user as someone who can code but has no prior context on the specific app or its concepts; assume nothing carries over from a previous session. Confidence: 0.9
- Point out tradeoffs and common pitfalls as they come up, especially around security (auth, env vars) and data integrity. Confidence: 0.9
- Gives short, terse go-ahead messages at phase boundaries (e.g., "start next phase") and expects the assistant to remember the established build rhythm and drive the next step from there without re-explaining context. Confidence: 0.6
- When the user issues a short/ambiguous correction, the assistant must not launch sweeping, unrequested changes based on its own reading of it — misreading "i meant groq" as a directive to swap providers triggered a full codebase provider swap that the user then had to stop ("i am not talking abt groq"). Ask a targeted confirming question before large reworks; don't chase tangents and lose what the user was actually asking. Confidence: 0.8
- Reports bugs by pasting verbatim framework/dev-console output (Next.js dev overlay with the exact error text, file:line, code frame, and call stack — numbered "1/3", "2/3" when sending several) instead of describing the problem. Treats console errors/warnings as real bugs: diagnose and fix directly from the paste, no clarifying questions needed. Confidence: 0.7
- Theme persistence must be server-rendered, never script-injected: store the theme in a cookie and render the `dark` class on `<html>` directly from the root layout. Do NOT inject a pre-paint theme script at all — neither a raw inline `<script dangerouslySetInnerHTML>` inside a component nor `next/script` with `strategy="beforeInteractive"` — because React 19 in Next 16 warns on script tags rendered inside components, and the cookie approach eliminates the script entirely with no flash (explicit user directive replacing the earlier beforeInteractive-based fix). Confidence: 0.9
